Monlingo 核心引擎：高級版面分析規格
版本: 5.0
日期: 2025年7月28日
狀態: 定稿

1.0 模組概述
本文件定義了 Monlingo 核心引擎中「高級版面分析 (Advanced Layout Analysis)」模組的演算法規格。

此模組的核心職責是接收來自 OCR 層的、原始且可能零散的文字辨識結果（包含文字內容及其邊界框座標），並將其智能地重組為一個結構化的、符合人類閱讀直覺的版面。最終輸出將清晰地劃分出畫面中的欄位 (Columns) 和段落 (Paragraphs)，為後續的翻譯和使用者介面渲染提供一個乾淨、有序的數據基礎。

本引擎採用三階段處理流程，以確保最高的準確性和穩健性。

2.0 處理流程架構
版面分析引擎的處理流程被嚴格劃分為三個獨立且依序執行的階段：

階段一：橫向行合併 (Horizontal Line Merging):

任務： 將因 OCR 辨識而產生的、在同一水平線上的文字碎片，拼接成語義上完整的單行文字。

輸入： 原始 OCR 結果列表 [(bbox, text, confidence), ...]。

輸出： 「完整文字行」列表 [{bbox, text, confidence, ...}, ...]。

階段二：智能分欄 (Intelligent Column Detection):

任務： 透過先進的「有序聚類」演算法，準確識別畫面中所有獨立的文字區塊或欄位，並將它們分離。

輸入： 階段一輸出的「完整文字行」列表。

輸出： 一個二維列表，其中每個子列表都代表一個獨立的欄位 [[line1, line2], [line3, line4], ...]。

階段三：段落分段 (Paragraph Segmentation):

任務： 在每一個獨立的欄位內部，使用加權評分系統，將連續的文字行組合成語義完整的段落。

輸入： 階段二輸出的欄位列表。

輸出： 最終的結構化版面數據，以字典形式呈現，包含所有欄位及其內部段落。

3.0 階段一：橫向行合併
此階段旨在解決 OCR 引擎可能將單行文字錯誤地分割為多個小框的問題。

3.1 演算法：兩階段嚴謹合併
對於每一對潛在的合併對象（例如 box_A 和 box_B），必須同時通過以下兩道關卡才能合併：

關卡一 (垂直重疊率):

計算兩個文字框在 Y 軸上的重疊高度。

合併前提： 只有當垂直重疊率超過 50% 時 (重疊高度 / 較小框的高度 > 0.5)，才進入下一關判斷。此舉可有效過濾掉垂直方向上明顯分離的文字框。

關卡二 (相對水平間距):

計算兩個文字框之間的水平像素間距 (horizontal_gap)。

計算這兩個框的平均字元高度 (avg_char_height) 作為動態的「尺」。

合併條件： 只有當水平間距小於平均字高的特定倍數時（例如 horizontal_gap < avg_char_height * 1.5），才認為它們的間距是合理的，並最終進行合併。

4.0 階段二：智能分欄
此階段採用「有序聚類 (Ordered Clustering)」演算法，以準確識別複雜佈局，同時保證閱讀順序。

4.1 演算法：有序聚類 (Ordered Clustering)
全局預排序 (Global Pre-sorting):

將階段一輸出的所有「完整文字行」，進行一次全局的「從上到下、從左到右」排序。這份排序後的列表將作為後續聚類過程唯一的、不可變的處理順序。

有序觸發「滾雪球」聚類:

為列表中的每一行建立一個 is_processed 標記（初始值 False）。

主循環： 從已排序列表的第一個文字行開始遍歷。若當前行未被處理，則將其作為一個新的欄位的「種子 (Seed)」，開始創建一個新的欄位，並將其標記為 True。

「滾雪球」子循環 (擴展欄位):

以「種子」行所在的 current_column 為基礎，反覆掃描整個原始列表。

核心判斷 (二維鄰近度)： 對於每一個未被處理的行，判斷它是否與 current_column 中已存在的任何一行在二維空間上「足夠近」。

「足夠近」的定義需要同時滿足以下兩個條件：

a. 垂直鄰近度： 兩個文字框的垂直間距小於一個相對閾值（例如 平均行高的 1.2 倍）。

b. 水平鄰近度： 兩個文字框的水平範圍有顯著的水平重疊（例如 重疊寬度 > 50%）。

吸納新成員： 如果找到一個滿足條件的行，就將其「吸納」進 current_column，並將其 is_processed 標記設為 True。

循環： 這個「滾雪球」過程會一直重複，直到某一次完整的掃描後，再也沒有任何新的行可以被吸納進來為止。

完成與重複：

當一個欄位的「滾雪球」過程結束後，該欄位就被最終確定。演算法回到主循環，尋找下一個未處理的行作為新種子，重複上述過程。

輸出: 一個列表的列表。其中每個子列表都代表一個獨立的欄位，且子列表的順序（即欄位的順序）嚴格按照它們在畫面中從上到下的位置排列。

5.0 階段三：段落分段
此階段在每個獨立的欄位內部，使用加權評分系統將行組合成段落。

5.1 演算法：加權評分系統
門衛檢查 (Gatekeeper Check):

硬中斷規則： 首先檢查相鄰兩行的垂直距離。如果 垂直間距 > 1.5 * 平均行高，則立即判定不合併，後續評分無需進行。

加權評分:

若通過門衛檢查，則根據以下指標計算合併分數（總分100）：

指標1：垂直距離 (+30 分): 距離越近，分數越高。

指標2：對齊風格一致性 (+30 分): 只要滿足左對齊或置中對齊中的任何一項，即可得分。

指標3：字體高度相似性 (+25 分): 兩行字高差異在 20% 以內，即可得分。

指標4：上下框寬 (+15 分): 上行寬度大於或約等於下行寬度，即可得分。

最終決策:

設定一個合併閾值（例如 75 分）。

只有當總分大於等於該閾值時，兩行才被合併到同一個段落。

6.0 最終輸出數據結構
本模組的最終輸出是一個結構化的字典，格式如下：

{
  "success": true,
  "layout": {
    "column_1": [
      {
        "paragraph_id": "para_1",
        "lines": [
          { "bbox": [[...]], "text": "...", "confidence": 0.95, "line_height": 20 },
          { "bbox": [[...]], "text": "...", "confidence": 0.92, "line_height": 21 }
        ],
        "bbox": [[...]] // 整個段落的合併邊界框
      }
    ],
    "column_2": [
      // ... 其他欄位和段落
    ]
  },
  "processing_time_ms": 15.7
}




為什麼最終輸出是結構化的字典?



您好，這是一個非常核心的問題，直接關係到我們設計這個版面分析引擎的根本目的。

簡單來說，最終輸出之所以是結構化的字典，是因為原始的 OCR 結果只是一堆無關聯的「文字碎片」，而我們的目標是將它們還原成帶有「結構」和「意義」的版面。結構化的字典是描述這種複雜結構的最佳方式。

讓我們來深入探討一下，為什麼一個簡單的列表（List）無法勝任，而字典（Dictionary）卻是必要的。

1. 為了表示「層級關係 (Hierarchy)」
一個畫面上的文字佈局，天然就存在著層級關係：

一個畫面 (Layout) 可能包含多個欄位 (Columns)。

一個欄位又包含多個段落 (Paragraphs)。

一個段落最終由多個文字行 (Lines) 組成。

一個扁平的列表 [line1, line2, line3, ...] 完全無法表達這種層級。而您在 PRD v5.0 中看到的結構化字典，則完美地用巢狀結構對應了這種關係：

JSON

{
  "layout": {          // <-- 層級 1: 整個畫面佈局
    "column_1": [      // <-- 層級 2: 欄位
      {                // <-- 層級 3: 段落
        "lines": [     // <-- 層級 4: 組成段落的文字行
          ...
        ]
      }
    ]
  }
}

這種結構讓後續的處理模組（如翻譯或渲染）能夠立刻理解：「哦，這幾行是屬於同一個段落的，而這個段落又是在第一個欄位裡。」

2. 為了「清晰易讀」與「方便擴展」
清晰易讀 (Clarity): 字典使用鍵值對 (Key-Value Pairs)，這使得數據本身就具備了自我描述的能力。當您看到 "column_1"、"paragraph_id"、"lines" 這些鍵（Key）時，您立刻就能明白它們代表的意義。如果我們用一個複雜的多維列表 [[[...]]] 來表示，程式碼會變得極難閱讀和維護。

方便擴展 (Extensibility): 如果我們未來想為「段落」增加一個新的屬性，比如「對齊方式」，我們只需要在段落物件中新增一個鍵值對 "alignment": "center" 即可，完全不會影響到現有的 lines 或 bbox 數據。這種擴展性對於軟體的長期維護至關重要。

3. 為了賦能「後續處理模組」 (最重要的原因)
這個結構化輸出，是後續所有高級功能的基石。

對於翻譯引擎：

之前（沒有結構）： 翻譯引擎只能拿到零散的句子片段，例如 "He couldn't read," 和 "but never gave up."，它只能逐句翻譯，結果可能生硬且不連貫。

現在（有了結構）： 翻譯引擎可以拿到一個完整的段落 "He couldn't read, but never gave up." 作為輸入。這提供了完整的上下文，讓翻譯結果更流暢、更準確、更像人類的語言。

對於 UI 渲染引擎 (您的 Windows 應用程式)：

之前（沒有結構）： UI 只能為每一個文字行，都畫上一個獨立的翻譯框。

現在（有了結構）： UI 接收到一個完整的段落物件後，它可以讀取這個段落中所有 lines 的 bbox 座標，然後計算出一個能包圍所有這些行的、統一的、大的邊界框。接著，它就可以在這個大框內，顯示完整的段落翻譯。這正是您想要的「融合」效果，而不是「併裝」。

總結來說，將最終輸出設計為結構化的字典，是整個版面分析引擎價值的最終體現。它不僅僅是數據格式的選擇，更是將一堆原始、無序的像素資訊，轉化為機器可理解的、帶有豐富上下文的結構化知識的關鍵一步。
