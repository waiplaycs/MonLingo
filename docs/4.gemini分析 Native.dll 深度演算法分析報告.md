Native.dll 深度演算法分析報告
一、摘要 (Executive Summary)
本報告旨在深度剖析 Native.dll 的內部工作流程與核心演算法。分析顯示，此 DLL 不僅僅是功能的集合，而是實現了幾個精心設計的、高效能的處理管線 (Processing Pipelines)。其演算法設計的核心思想是高效能與精確控制，透過將複雜任務放在原生 C++ 層處理，為上層 .NET 應用提供簡潔的 API 介面。

本報告將重點分析三個核心演算法：

OCR 處理管線：一個從初始化、圖像預處理到結果解析的完整流程。

畫面擷取管線：採用了現代 Windows API 的非同步、事件驅動模型。

安全與完整性驗證演算法：一個在啟動時執行的自我檢查機制。

二、我的分析方法
我將模擬一位逆向工程師，透過以下幾種靜態分析技術來解讀這個 DLL：

結構解析：讀取 PE 檔案的區段、匯入/匯出表，確定其依賴和提供的功能。

字串關聯：將內嵌的純文字字串（如日誌、錯誤訊息）與特定的函式關聯，以推斷其功能。

API 模式識別：識別出一系列 Windows API 呼叫的組合，並根據我的知識庫（包含大量關於 Windows 開發的資料）推斷出它們所實現的特定設計模式（例如非同步回呼模型）。

邏輯流程推導：基於函式之間的呼叫關係和字串線索，重建出高階的邏輯流程圖。

三、核心演算法 1 - OCR 處理管線 (The OCR Pipeline)
從匯出的 ocr_* 函式和內嵌字串 RunOcrPipeline 來看，其 OCR 功能並非單一函式呼叫，而是一個分階段的管線。

演算法流程推斷：

初始化 (ocr_init):

細節: 這個函式接收初始化選項 (CreateOcrInitOptions)。從字串 OcrInitOptionsSetUseModelDelayLoad 推斷，它包含一個模型延遲載入的選項。這是一個最佳化演算法：如果使用者暫時不用 OCR，就不會將數百 MB 的模型載入到記憶體中，從而加快應用啟動速度。

動作: 載入 OCR 模型檔案，初始化 PaddleOCR 引擎，並設定基本參數。

圖像預處理 (在 RunOcrPipeline 內部):

細節: 匯出函式中有 GetImageAngle。這意味著管線內部包含一個圖像方向校正的演算法。它會先偵測圖像中文字的傾斜角度，然後將圖像旋轉到水平位置，這能極大地提升 OCR 的辨識準確率。

其他細節: 從 OcrProcessOptionsSetResizeResolution 等字串推斷，它還會對圖像進行縮放 (Resize)，將其調整到 OCR 模型最擅長處理的解析度。

管線執行 (RunOcrPipeline):

細節: 這是演算法的核心。它接收處理好的圖像和處理選項（CreateOcrProcessOptions），然後執行一個完整的序列：文字偵測 (Text Detection) -> 文字方向分類 (Angle Classification) -> 文字辨識 (Text Recognition)。

演算法: 文字偵測很可能使用了像 DBNet 這樣的演算法來找出圖像中所有文字塊的邊界框 (Bounding Box)。然後對每個文字塊進行辨識。

結果解析與存取:

細節: RunOcrPipeline 執行完畢後，會回傳一個複雜的結果物件的指標。上層的 .NET 程式不能直接讀取這個 C++ 物件。

演算法: 因此，DLL 提供了一整套「存取器 (Accessor)」函式 (ocr_get_line_count, ocr_get_line_content, ocr_get_word_confidence 等)。這是一種常見的跨語言設計模式。主程式透過這些函式，安全地、逐條地從原生記憶體中取出辨識結果，避免了複雜的記憶體管理問題。

四、核心演算法 2 - 高效畫面擷取管線 (Graphics Capture Pipeline)
從 windows.graphics.capture 相關字串和 d3d11.dll 的依賴來看，它使用了目前最高效的 Windows Graphics Capture API。

演算法流程推斷 (非同步事件驅動模型)：

初始化 (screenshot_window_loop_start):

細節: 這個函式接收一個視窗控制代碼 (HWND)。其內部演算法流程為：

呼叫 CreateCaptureItemForWindow 將 HWND 轉換為 GraphicsCaptureItem。

使用 Direct3D11CaptureFramePool 建立一個畫面訊框池。

建立一個 GraphicsCaptureSession。

關鍵一步：為訊框池的 FrameArrived 事件註冊一個 C++ 回呼函式 (Callback)。

呼叫 session.StartCapture() 開始擷取。

非同步擷取 (由系統觸發的回呼函式):

細節: 一旦有新的畫面訊框準備好，Windows 會自動呼叫 DLL 內部註冊的那個回呼函式 (從日誌字串 OnFrameArrived 可以確認)。

演算法: 在這個回呼函式中，DLL 會從事件參數中獲取 D3D11 紋理 (texture)，這是一個在 GPU 記憶體中的影像。然後，它可能會執行一個 GPU 到 CPU 的記憶體複製操作，將影像資料轉換成 OCR 引擎可以處理的格式（如 BMP 或 PNG 的記憶體流），並將其存儲在一個共享的緩衝區中。

資料讀取 (screenshot_window_loop_read):

細節: 上層的 .NET 程式會定期呼叫這個函式。

演算法: 這個函式的作用非常簡單：它會鎖定共享緩衝區，然後將最新的畫面影像資料複製出來，回傳給 .NET。

這個生產者-消費者模型 (Windows API 是生產者，.NET 程式是消費者) 是實現低延遲、不影響遊戲效能的即時畫面擷取的最佳實踐演算法。

六、結論與分析限制
Native.dll 是一個高度最佳化的原生模組，其演算法選擇體現了對效能和現代 Windows API 的深刻理解。

分析限制:

具體參數未知：我們知道它使用了 PaddleOCR，但不知道開發者使用了哪個特定版本的模型，以及在初始化時傳入了哪些最佳化參數（例如，是否啟用了 INT8 量化來加速推理）。

演算法細節黑箱：像 k-means 這樣的演算法，我們只知道它被提及，但無法僅從二進位檔案中還原其具體的應用場景和實現細節。

變數與註解丟失：所有原始的變數名稱、函式內部註解都已丟失，這使得理解程式碼的商業邏輯變得更加困難。

儘管有這些限制，我們依然可以清晰地看到其核心演算法的骨架和設計哲學，這為您的開發提供了極具價值的參考。
